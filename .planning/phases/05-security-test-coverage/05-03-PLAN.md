Add 2 new test cases to the existing `describe('calendlyRequest', ...)` block in `src/lib/calendly.test.ts`.

**Test 1: "propagates error gracefully when refreshAccessToken throws during 401 recovery"**

This tests that when a 401 triggers a refresh attempt, and the refresh itself fails (e.g., expired refresh token, Calendly API down), the error propagates cleanly without crashing.

Setup:
- `prisma.user.findUnique` returns user with encrypted tokens (same pattern as existing tests)
- `requestFn` rejects with a 401 error (same `axios401Error` pattern as existing test)
- Mock `axios.post` (the refresh call) to reject with a new Error, e.g., `new Error('Refresh token expired')`

Assert:
- `calendlyRequest('user-123', requestFn)` rejects — use `await expect(...).rejects.toThrow()`
- The error message should contain 'Refresh token expired' (the refresh failure propagates, not a generic crash)
- Restore the axios spy after the test

**Test 2: "retry after 401 refresh uses the NEW access token, not the old one"**

This explicitly verifies that after a successful refresh, the retry call passes the new token.

Setup:
- Same pattern as existing "uses decrypted refresh token on 401" test
- `requestFn` is `vi.fn()` that rejects first with 401, then resolves
- Mock `axios.post` to return `{ data: { access_token: 'brand-new-token', refresh_token: 'brand-new-refresh', token_type: 'Bearer', expires_in: 7200, created_at: Date.now() } }`

Assert:
- `requestFn` was called exactly 2 times
- First call: `requestFn` called with the OLD decrypted access token ('real-access-token' or whatever the decrypt mock returns)
- Second call (retry): `requestFn` called with 'brand-new-token' (the NEW access token from refresh)
- Use `requestFn.mock.calls[0][0]` and `requestFn.mock.calls[1][0]` for exact argument checks

These tests use the same mock patterns already established in the file (vi.mock '@/env', vi.mock '@/lib/encryption', vi.mock './prisma', axios spy). No new mock infrastructure needed.
